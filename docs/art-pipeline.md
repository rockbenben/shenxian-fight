# 美术出图管线

美术是可选增强层：游戏本体永远用骨骼胶囊/锥形笔锋渲染，**逐件独立挂载**——
`public/chars/<id>/` 下存在哪个部件的 PNG 就用哪张贴图，缺的部件各自回退到
程序化绘制，不会崩、不会露洞、不需要任何开关。目录整个不存在时，效果等同
全部部件都缺，即完全回退成当前的纯程序化渲染。

## 0. 结论先行：只做头 + 躯干，不做四肢

Task 27 用占位图验证过，结论是**四肢不值得出图**，只生成 `head.png` +
`torso.png` 两张，每角色出图量从 6 张降到 2 张。理由是挂载尺寸：

| 部件 | 实际挂载尺寸 | 说明 |
| --- | --- | --- |
| 头 | 约 32×32 px | 独立一张 |
| 躯干 | 约 40×56 px | 独立一张 |
| 手臂/腿 | 约 22×26 / 26×32 px | **同一张图会被分别拉伸到大臂/小臂或大腿/小腿两段** |

四肢那张图不仅本身就小到画不出细节，还要同时兼容两段不同长度的骨骼拉伸，
画再精细也只会被压成一根均匀色管——花在四肢上的出图成本基本打水漂。角色
辨识度（这是哪吒还是悟空）全靠头（脸/发髻/抹额）和躯干（衣着/配色），这两
块才值得花生图配额。四肢继续用程序化笔锋渲染（见下节）。

### 0.1 程序化四肢长什么样（以及为什么它不是一根色管）

头和躯干是画出来的厚描边厚涂素材，四肢却是代码画的。**画法不对的时候，
这一层是整个画面最扎眼的地方**——不是难看，是"这是另一个人身上贴的纸片"。
实测踩过的三处，都在 `renderer.ts` 的 `seg()` / `fillTapered()` / `drawFoot()`：

1. **四肢必须是柱体，不能是平涂色管。** 躯干素材有块面阴影，四肢平涂，
   两边并排时像"手是后贴上去的"。`limbGrad()` 沿骨轴两侧给一道横向渐变，
   受光侧由光照方向在**垂直骨轴的轴上**解出来（不是按世界坐标的上下）——
   柱子转怎么转，高光都在该在的那一侧。另有一道明暗差下限（`MIN_ROUND`）：
   真实光照算下来竖直肢体两侧只差 0.34，在这个尺寸（角色 150px、肢体宽 9px）
   画出来等于没画，圆柱感靠的是那个下限。

2. **前臂不能直接用 `accent`。** 十二个角色的 accent 大多是**近白的浅色**
   （铁扇 #eef3ea、后羿 #f2efe6、雷震子 #f0f4ff、二郎 #e8ecff、白骨精 #e8e4d6），
   拿它画满整条前臂等于在身上横着贴一条白带子，选人卡尺寸上比脸还亮。
   现在取 `main` 与 `accent` 的对半：仍是"浅袖 + 深衣"的两截配色，亮度落回角色自己的色系。

3. **肘/膝上不能横着一道黑带。** 每节骨段各自描一圈墨色边，圆头帽就落在关节上，
   于是每个关节都有一道横贯的黑杠。`taperedPath()` 的 `capStart=false` 只在**描边**时
   省掉起点那道弧（填充仍要圆帽，否则接缝是个平切的口子）；起点一定被下一段更粗的
   骨段或躯干整个盖住，省掉是安全的。

另外**腿要落地**：此前小腿是一根收尖的笔锋直接怼到地面线上，读起来像角色被钉在那里。
`drawFoot()` 从踝点长一只脚掌（脚掌保持水平，屈膝时它该是平的；空中翻滚时随人物整体
旋转，读作收脚蜷腿）。脚比"小腿一半粗"要小——第一版就栽在这里，出来是两块方砖。

5. **飘带不能甩成一柄白刃。** 十二个角色的 `adorn.sashes[].tip` **几乎全是近白的浅色**
   （铁扇 `#eef3ea`、悟空 `#fff6e0`、后羿 `#f2efe6`、白骨精 `#e8e4d6`、二郎 `#dfe8ff`）。
   带子甩出去时梢部比脸还亮；再叠上原先那条几乎不收的锥度（梢部还剩 55% 宽），
   整条带子在角色旁边横成一枚**两头钝的梭子**——恰好是剑刃的形状。铁扇公主一跳，
   屏幕上就是一把飞出去的白色兵器。
   两条都收：梢色对半（`mix(color, tip, 0.45)`，保留两截渐层，亮度落回角色色系），
   锥度改走平方曲线（根部几乎不收、末端收到 35%；一路收到 25% 那档实测收成了鞭梢）。

> 改这一层时**先实拍再看**：这四条在代码上都成立，但合起来是什么读法只有截图说了算。
> 开发服务器 `npm run dev` 起在 5199，`?dp=select` / `?dp=training&me=<id>&dummy=stand`
> 能直接落到选人页与陪练场，取景脚本见 `design-preview/shots.cjs`（支持裁剪放大）。

`parts.ts` 本身仍然支持逐件挂载任意子集——如果某个角色确实需要更强的四肢
辨识度（比如武器要贴在手上），照样可以补 `armF.png` 等文件，回退规则一视
同仁，不需要改代码——**前提是文件名在 `src/render/parts.ts` 的 `NAMES` 探测列表里**。
那张表现在只有 `head`/`torso`（理由见本文第 0 节：四肢不出图，探七件等于每个角色白付 5 个 404）。
要加四肢或兵器素材，除了放文件还得把名字加回那张表，否则它不会被加载、也不会报错。

## 1. 生成角色立绘

用 `ai-image-gen` skill 生成角色立绘：扁平厚描边卡通风、正侧身战斗站姿，纯色背景，
头部与躯干轮廓清晰分离（互不遮挡，方便下一步切件）。

Prompt 模板：

```
东方神话角色<名字>，扁平插画风格，粗黑描边，横版格斗游戏站姿侧身像，
纯白背景，半身可见（头肩至腰），鲜艳配色<主色>
```

**描边粗细要控制**：程序化四肢的描边固定 2px（`INK.ink`，逻辑像素）。贴图
的描边如果明显比这个粗（占位图验证时踩过这个坑，占位图描边给到 6~7px），
放在一起头/躯干会比四肢"重"一档，读出来是两种画风拼接，而不是同一角色。
出图或后期都要把描边粗细往程序化四肢的水平上收。

## 2. 切件

从立绘上切出两个部件，每件独立 PNG、透明背景：

| 文件名 | 部位 |
| --- | --- |
| `head.png` | 头 |
| `torso.png` | 躯干 |

（如确有需要，`armF.png`/`armB.png`/`legF.png`/`legB.png`/`weapon.png` 仍是
合法文件名，挂载规则与 head/torso 完全一致——见下方"挂载与回退规则"。）

切件要点：
- 切口留 10% 重叠余量，避免旋转到极限角度时关节处露出背景缝隙。
- 部件图整体按「宽度方向撑满、高度方向沿骨骼方向」设计：躯干挂载时会被
  缩放成宽 ≈ 40、高 ≈ 骨骼长度（`SHOULDER_Y - HIP_Y`）；头挂载时是固定
  32×32 的正方形，画的时候留够这个长宽比的余量。
- **躯干锚点方向：画面顶部 = 肩线，画面底部 = 腰线，不留边距**（`renderer.ts`
  的 `drawBoneImg(ctx, shX, shY, hipX, hipY, ...)` 起点=肩、终点=腰，与
  `parts?.torso` 挂载调用一致）。这个方向曾经反过来过——旧版调用是
  `drawBoneImg(ctx, hipX, hipY, shX, shY, ...)`（起点=腰），实测会把整张图
  在挂载时做一次 180° 点反转（画面顶部→腰、画面底部→肩，且左右也一并翻转），
  用一张四色象限测试图挂进 `#training` 截图验证过（Task 27 第二轮修的）。
  素材按「肩在上、腰在下、面朝右」自然画即可，不需要为了迁就挂载方向反着画。
- 躯干整个衣物形状要撑满画布（肩线贴顶、腰线贴底、宽度占满大部），不要画成
  "挂在画布中央、四周留白的服装展示图"——四周留白会在拉伸挂载时被压扁成
  真身体只剩一小条，甩出轮廓外的飘带/流苏/下摆反而被拉成视觉主体。
- 尺寸建议给到实际挂载尺寸的 3–4 倍（头 128×128、躯干 160×224），留缩放
  余量，做完之后确认缩小到实际游戏尺寸（角色约 150px 高）时五官仍然可辨——
  细节太碎会被缩没，眼睛/发型这类关键特征要画得够粗够大。

## 3. 朝向与镜像：只画一份，「面朝右」为准

游戏里角色会不断转身（每帧自动面向对手），但每个部件只有一个文件——没有
`head-left.png` 这种左右两份。转身时贴图靠代码镜像，不是靠美术出两套图。

**约定：所有部件图都按「角色面朝右」的姿势画**（Prompt 模板里的站姿侧身像默认就是
朝右）。面朝左时，引擎会把每一节骨骼各自的贴图内容在自己的锚点上做一次水平镜像
（不是简单旋转——旋转到骨骼方向只能保证贴图落在正确的位置和角度，画面内容本身
左右不对称的部分不会跟着换边，必须额外镜像一次）。这意味着：

- **非对称细节按"角色朝右站立"时应该出现的那一侧画**，比如哪吒的抹额飘带、
  二郎神的三只眼按朝右的姿势画。转身朝左时，花纹、朝向细节会跟着头/躯干一起
  翻到镜像位置，不用也不能手工再画一份"朝左版"——多画的朝左版反而会被再镜
  像一次，变成两次翻转，回到错的那一侧。
- 镜像是逐骨骼独立做的（躯干/头各自绕自己的锚点镜像，不是整个人物绕一个中
  心整体翻转），只要素材已经按「关节到关节」画好，镜像后关节位置依然精确
  对齐，不需要额外处理。Task 27 用占位图实测过这条镜像链路（非对称的抹额飘
  带 + 躯干腰带结都正确跟随 facing 翻面），结论成立。

## 4. 挂载与回退规则

放入 `public/chars/<charId>/`，文件名固定为 `head.png` `torso.png`（+ 可选的
`armF.png` `armB.png` `legF.png` `legB.png` `weapon.png`）。`charId` 对应
`src/data/characters/` 里角色的 `id` 字段（如 `wukong`、`erlang`、`niumo`、`nezha`）。

游戏在角色出场时会自动探测这一路径（`/chars/<charId>/<part>.png`）。**规则是
逐件独立的**：探测到哪个部件的图就用哪张贴图，缺的部件各自静默回退成当前的
程序化绘制（头→圆形胶囊，躯干→锥形笔锋，四肢→锥形笔锋），不影响可玩性，
不会半吊子拼接出"贴图缺了一半、旁边露出背景色"这种情况，控制台也不会报错
（图片加载失败走的是 `onerror`，不是异常）。目录整个不存在时，两个部件的探测
全部落空，效果等同完全回退到纯程序化渲染，和 Task 27 之前的行为一致。

### 4.1 头身比：贴图是「脸 + 装饰」，倍率要**按脸**给

头贴图不只有脸。哪吒的抹额飘带、二郎神的天冠、铁扇公主的高髻、白骨精的头饰，
各自在内容框里占一大块。而 `headScale()` 归一的是**整幅内容盒**——于是装饰占得多的人，
脸就小：实测同一副骨架下，哪吒的脸在屏幕上只有 15.6 逻辑单位宽，猪八戒是 24.5，
**差 1.57 倍**，而两人的身体一模一样。哪吒是小孩，脸小 + 身体大 = 头身比例不对；
铁扇公主则被高髻拉成一条竖板。

所以每个角色有一个 `build.head`：**按脸量出来的**缩放倍率（量的是脸在素材里的
宽×高，几何平均，目标 21 逻辑单位；数值见各角色文件里的注释）。素材重出或重切之后，
倍率要重量一次——`tests/headProportion.test.mjs` 会先响（它自带一张"脸在哪"的表，
表里的数也要重新量），量法与工具见 `design-preview/head-grid.py`。

**出图时头要留够余量**：脸之外那些装饰（飘带、天冠、高髻）是**跟着一起放大**的，
所以一张飘带甩得很远的头，脸上的像素就得画得更足，否则放大之后五官糊成一团。

## 5. 提示词的坑（每一条都是烧过配额换来的）

**约定写在文档里不等于写进了提示词。** 第 3 节的「面朝右」立了很久，而
`gen-parts.py` 里八处躯干一直写着 `Front view`——头三分侧面、身子正对镜头，
挂到侧身骨架上就是纸片人（雷震子那张最典型：两只翅膀左右平摊）。
接连两轮重出素材都把错的朝向烙得更深。现在有 `tests/artOrientation.test.ts` 挡着。

| 症状 | 成因 | 措辞 |
|---|---|---|
| 出正脸 | 只写 `Three-quarter view facing right` 太笼统；加否定句「不要正脸」也无效——**纯否定句只让模型退回最安全的选项** | 写成可执行几何：鼻梁压过远颊线、远颊被部分遮住、近耳全见远耳不见 |
| 整个头躺倒 90° | `rotated 35 degrees` 被理解成**旋转画面** | 写明转轴：头保持竖直、下巴水平、绕颈部**竖轴**水平转 |
| 并排画了两颗头 | 描述视角的措辞本身在暗示「多给几个视角」，包围盒把两颗都框进去，切出来是横条 | `one subject alone, not a character sheet, no side-by-side panels, no duplicates` |
| 整张脸被染成角色色 | `teal and white palette` 被应用到全图，出来是没有肤色的单色线稿 | 圈定范围：配色只管头发/冠饰/衣领，脸保持自然肤色；非人肤色（雷震子青绿、白骨精惨白）写明例外 |
| 躯干宽扁，挂上去横向压扁 | 模型默认把衣服画成一件摊开的平面 | 长宽比是**硬约束**不是构图偏好：挂载横向铺到 40、纵向铺到骨长 68，两轴独立，内容长宽比必须≈0.588 |
| 全员出图判成 TIMEOUT | 完成判据写死 `naturalWidth > 800`，那是照横图 1264×848 定的；提示词改成竖构图后模型出 617×1024，宽度不到 800 | **构图要求和完成判据是耦合的，改一个必须回头看另一个**。判据改用长边 |

**为解决问题 A 加的措辞，在 A 换了解法之后必须撤掉。** 「双颊可见」是早期为了让
铁扇公主的脸别太窄加的；等头改成按面积归一之后它就没用了，却一直留着，
并且在反向把模型往正脸拽——朝向卡了两轮都没找到原因。

**超时不等于没出图。** 判据认错时图往往已经生成，配额已经花掉。
`scripts/rescue.py` 把标签页上现成的图裁进 `_raw/`，零配额找回。

# 关卡远景出图管线

舞台此前是**纯程序化**的：一条天空渐变、三层剪影山形、一层氛围粒子（见
`src/render/renderer.ts` 的 `drawBg`）。它便宜、它会视差，但它是"程序画的"——
远山没有细节、远近只靠"谁更黑"来读，整幅画面是平的。这是这个项目"不够美"最大的单一来源。

## 0. 结论先行：远景是**一幅背板**，不是一条带

这一条是踩出来的：第一版把画裁成"地平线以下的一条带"塞进画面中段，
十二关实测下来全是三条横带（渐变天 / 一条外来画带 / 黑山带）——
画与舞台各说各话，调色也救不回来（那版试过双色调、压色阶、去饱和，
每一步都只是让"另一张画"更像"另一张画"）。

现在远景是**整幅背板**：画铺满"视口顶 → 地面线"这一整块，它自己的天空、自己的远山、
自己的地面都在里面；程序化的星辰与月亮画在它**上面**；角色站在画里的地面上。
舞台自己的天空渐变、云纹、山形剪影在有画时**全部退场**——一份背景只留一个来源。

于是后处理只剩一件事：**把画的颜色拉进这一关的色板**（按色相相乘 + 去饱和 + 压暗），
形一概不动。

## 1. 挂载与回退规则

放入 `public/stages/<stageId>/far.webp`，`stageId` 对应 `src/data/stages.ts` 的
`HOME` 键（ nezha / erlang / wukong / niumo / honghaier / tieshan / baigu / houyi /
leizhen / zhongkui / xingtian / bajie）。

游戏在每一关开画时探测这个路径（`src/render/stageArt.ts`）。**规则与角色部件一致：
逐层独立**——far 有图就用图，没有就回退到程序化剪影，不报错、不露洞、不影响可玩性。
整个 `public/stages/` 目录不存在时，效果等同完全没有远景美术。

为什么是 webp：十二张远景要进离线包（游戏承诺离线可玩），png 存这种大色块图每张
300~500KB，webp 同一张 25~45KB。`vite.config.ts` 的 precache 清单因此加了 `webp`。

## 2. 出图：两条通道，同一份提示词

提示词与关卡清单放在 **`scripts/stage-art.json`**（两条通道共用，不各写一份）：

```
node scripts/gen-stage-art-matrix.mjs              # MiniMax Matrix 通道，一条命令就能跑
python scripts/gen-stage-art.py                   # Gemini 网页通道，走仓库既有的 CDP 管线
python scripts/gen-stage-art.py nezha niumo       # 点名重出
python scripts/gen-stage-art.py --postprocess     # 只做后处理（改了调色时用，零配额）
```

后处理在 `scripts/gen-stage-art.py` 的 `postprocess()`，两条通道共用。

产物分两段，与角色部件管线同一套规矩：**出图（烧配额）与后处理（可重跑）解耦**——
原生分辨率先落到 `_raw/stages/<id>.png`，后处理随时重跑，不该再出一张图。

## 3. 后处理：三步

1. **不裁**。原图就是 16:9（2752×1536），构图完整留着：上半是提示词要来的"空天"，
   下半是远方的大地。裁任何一刀都会把地平线或天空切掉半边。
2. **按色相调色**：把画乘上这一关的主色（天色），除以主色自己的亮度——亮度结构原样保留、
   只有色相被拉过去；再压暗一档（远景是背景，不该跟角色抢亮度）、往地面色沉一点
   （整幅画与舞台同一口气）、去饱和 28%（按色相相乘会把某个通道顶上去，
   花果山的绿、射日台的橙一度艳得不像夜里）。
3. **不量化**。把画量化成几个平色块再映到色阶上，形状会糊成一团（石牌坊、竹子、
   屋顶全成了同色的块）——那是"把画变成剪影"的路子，而这一版画要保留自己的形体。

最后压成 webp（1280 宽，q80）。

## 4. 画面里的读法（比提示词本身更重要）

- 远景是**背板**：宽度按视口取（宽屏时两侧裁掉），高度不够时按高度放大——
  **纵向构图必须完整**，裁掉上半会把画里的地平线也裁没。
- **背板必须盖满整个可见视口**，不能只盖到地面线为止。地面线在**世界坐标**里，
  而镜头缩放（放大招时 1.25~1.45）会把它推到屏幕更下面去：两者之间露出一条谁都没画的缝，
  上一帧的像素就留在那里——画面上是一条横贯全屏的彩色乱码带，镜头一动它就闪。
  （实测：把背板改回"只盖到地面线"，同一次大招演出里那条带立刻复现。）
- **缩放只跟视口走，平移才跟镜头走，且对齐到整数像素**。每帧按 camX 改一点点缩放，
  图会被反复重采样，山脊线、牌坊雕花那些细边缘会跟着一起抖——那是"背景一直在闪"的另一半来源。
  缩放固定后重采样的相位也固定，画面不再抖。视差取 0.01：镜头横移几百像素才挪动 1px。
- 星辰与月亮画在背板**上面**：它们是天空里的东西，画的天是实的，正好接住。
- 有远景时**不画**舞台的渐变天、云纹、山形剪影：一份背景只留一个来源，
  两层天空叠在一起反而脏，而山影压在画上会把画压成"一条带"。
- 氛围粒子（流萤/火星/竹叶）照旧画在最上层——它们在角色与画之间，是空气。
- **辉光阈值 3.4**：远景画成背板之后，画面里大片中亮度的雾也会被烤成一团团光斑，满屏都是
  "闪光"，而真正该发光的只有月亮、火焰与招式特效。阈值调高之后只剩很亮的东西在亮。

## 4.1 调色：先定亮度，再拉色相（顺序反了会白屏）

远景要拉进这一关的色板，但**不能直接按主色相乘**：

- 饱和红的亮度上限只有 0.299×255。先相乘的话红通道被顶到 255 截断——熔岩洞那张满屏橙红
  就是这么来的；截断之后再压暗已经救不回来。
- 换一种写法（"主色 ÷ 主色亮度 × 目标亮度"）同样会炸：主色亮度只有 51 时，除出来是 5 倍，
  目标亮度 200 乘上去是 1000 → 三个通道全溢出 → **整屏变白**（这一版真的白过）。

正确的次序：

1. **色相归一化**：主色除以它最大的通道，得到纯度方向 `(cn_r, cn_g, cn_b)`。
2. **算这个色相能承载的最大亮度** `lmax = 255 × (0.299·cn_r + 0.587·cn_g + 0.114·cn_b)`。
3. **目标亮度** = 色调曲线给出的值（gamma 1.28 × 0.8），再被 `lmax` 封一次顶。
4. 目标色 = 纯度方向 × 目标亮度，与原色按 55% 混。

出图的亮度差别极大（熔岩洞满屏亮橙、白虎岭大半是灰），单一系数压不住：压轻了熔岩关亮得把
角色吞掉，压重了别的关全糊成黑。曲线压的是中调与高光，黑场不受影响。

## 5. 体型：四肢为什么不再是一套模具

十二个人的头与躯干是画出来的厚描边厚涂素材，**四肢却是程序化画的**——而且十二个人**共用
同一套几何**：同样粗、同样锥度、同样长度、同样一颗圆手，只有颜色不同。

于是十二个人看着像同一副假人换了个色：猪八戒的胳膊和哪吒的一样细，白骨精的手和孙悟空的
一样圆。这不是"画得不够好"，是**同一副模具**。

修法是数据驱动的差异化（`CharacterDef.build`）：

| 字段 | 作用 |
| --- | --- |
| `arm` / `leg` | 四肢粗细倍率。1 = 现状。猪八戒 1.5、白骨精 0.7、哪吒 0.85 |
| `hand` | 手：拳 / 爪 / 掌 / 骨手。手是隔着屏幕认人的第一眼——比脸还小，但它一直在动 |
| `sleeve` | 手臂上的装束：袖口 / 护腕 / 毛边。光溜溜的锥形色管是"假人"的主因，袖口与毛边是最快的解 |

**为什么不给每人出四肢贴图**（这一条与上面第 0 节的结论同源）：

- 一张肢体图要同时拉伸到上臂与前臂两段长度，细节全被拉没——出图解决不了"变形"，
  只解决"表面"。
- 出图要迁就每个角色的配色与描边粗细（素材描边中位 1.25、四肢描 1.5），对齐的坑比角色部件
  那轮还多（`docs/art-pipeline.md` 第 5 节记着出正脸、朝向、裁切三类坑）。
- 而"假人感"的根源是**几何一样**，不是表面不够细。几何这件事用数据改一行就够，
  用 24 张图改不了。

十二个人的体型都写在各自的 `src/data/characters/<id>.ts` 里，注释写明为什么是这个数
（猪魔王：全场最粗的胳膊；白骨精：最细，手是骨手；猴王：手臂有毛、末端是爪）。

## 6. 骨架本身的三处毛病（与美术无关，是几何）

"看着像假人"里有一半不是美术的问题，是**骨架**的问题。三处都改了：

### 6.1 关节处有台阶

四肢每段是各自独立的锥形笔触，两段在关节处**半径对不上**：大腿收细到 3.6，小腿却从 5.5 起步，
于是膝盖的轮廓线上多一级折角，像接错了一节（实测截图上非常明显）。

改成**相邻两段首尾相接**（`LIMB_R`：肩 11 宽 → 肘 8 → 腕 5；髋 13 → 膝 10 → 踝 6）。
渲染层导出这份半径，测试也引同一份——两处各写一份数，迟早漂。

### 6.2 头浮在身体上方

根因不是挂载算错，是**躯干贴图的上缘是透明的**：领口画在贴图上边以下（V 领），于是头贴图的底边
与领口之间总会露一线背景（实测 4 个逻辑单位）。

补一段**脖子**（`drawNeck`）：上端伸进头里 5、下端伸进躯干里 7，两头都藏进去，缝就没了。
颜色取 `accent`——那本来就是程序化圆头用的颜色，也就是这套画法里这个角色的"肤色"。

### 6.3 只有一只手

躯干宽 40、后臂宽 11，同根同向画就整根埋在躯干里——画面上就是"只有一只手"。
后侧手臂整体往身后挪 17（`FAR_ARM_DX`），从躯干后缘探出来，肩那一端仍压在躯干后面。

另外**兵器画在躯干之前**：兵器柄从身前横过胸口时，压在躯干上会读成"兵器穿过身体"；
放到躯干之后，柄被身体盖住，只有伸出去的那一截可见。
